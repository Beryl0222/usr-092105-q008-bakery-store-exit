# 烘焙门店退场清算平台

以品牌退场负责人面对的真实困局为起点：**储值金能跨店消费、蛋糕定金进了加盟商账户、冷柜属于租赁公司、中央工厂还按未来七天备料、员工最后班次和房租仍在持续产生**。本平台用只追加的领域事件把这些事实分开记录、按序处理，并为每个关闭案件维护一张随事实变化的未结清单与五个必须逐项关闭的交接闸门。

## 设计原则

1. **先分清主体与权利义务，再谈清算** — 品牌、加盟商、租赁公司、中央工厂、供应商、房东、顾客各是各的权利主体；钱在谁手里、资产归谁、损失谁承担，在 `LEGAL_ENTITY_IDENTIFIED` 里先固定。
2. **顾客自主选择，不替顾客做主** — 公告给出承接与退款两条路和选择期；逾期未选按公告默认退款，门店不得替顾客默认转邻店。
3. **邻店承接双校验** — 必须顾客本人确认（`CLAIM_TRANSFER_CONFIRMED.customer_confirmed=true`），且邻店当日仍有产能（`reserved_orders` 对每日承接上限做校验）。
4. **食品安全与租赁边界** — 临期食品只能捐赠 / 员工安全食用 / 销毁 / 退回工厂，禁止为抵债转卖；租赁冷柜不属于门店，处置请求直接拒绝并留痕，只能预约归还、由租赁公司签收。
5. **争议不株连无争议余额** — 加盟争议只能就争议金额挂账或提存；超范围冻结请求发 `FREEZE_REQUEST_REJECTED` 事件拒绝并留痕。
6. **付款严格按瀑布，流水只追加** — ① 顾客退款 → ② 工资 → ③ 房租水电 → ④ 供应商 → ⑤ 加盟结算；高顺位有无争议未付，低顺位不能付。错付用 `PAYMENT_REVERSED` 红冲，旧流水保留；争议金额发 `AMOUNT_ESCROWED` 提存至监管账户。
7. **重复通知只立一案** — 同一顾客同一权益的多渠道来函（门店登记、客服工单、商场转告、加盟商名单）以 `CLAIM_NOTICE_MERGED` 并入既有 claim；同一 `event_id` 重发幂等吸收，内容不一致则拒绝（旧记录不可改）。
8. **最终关闭有硬门槛** — 订单、食品、员工款项、租赁资产、供应商责任五个闸门（`HANDOVER_GATE_CLOSED`）必须**事实齐备 + 有交接凭据**双重满足，且未结清单清空，才能 `CASE_CLOSED`。

## 四个聚合（不新增聚合，各方通知归入这四类事实流）

| 聚合 | 承载事实 |
| --- | --- |
| `closure_case` | 公告、主体识别、持续计提（工资/房租）、邻店承接名单与产能、工厂停料、闸门与最终关闭 |
| `customer_claim` | 顾客权益登记、重复通知合并、顾客选择、承接确认、订单转移、退款核定、结案 |
| `inventory_disposition` | 食品/包材批次登记、安全处置、违法处置拒绝留痕、租赁资产预约归还与签收 |
| `settlement_payment` | 款项登记、资金归集、争议登记、越界冻结拒绝、支付/红冲/提存流水、争议认定、供应商方案 |

完整事件类型与载荷契约见 [`contracts/domain.schema.json`](contracts/domain.schema.json)；事件归属聚合由校验器强制（`src/validator.js`）。

## 未结清单（投影自动派生，不写库）

`projectCase()` 把一案件的全部事件折叠成当前视图，未结事项自动落入四桶：

| 桶 | 内容 |
| --- | --- |
| **等待顾客选择** | 已登记但顾客尚未在选择期内选择承接或退款 |
| **等待承接** | 已选转移、待顾客确认/产能校验，或已确认待邻店实际履约 |
| **待支付** | 退款义务、工资、房租、水电、无争议供应商货款等；已提存的争议部分不再列入 |
| **责任争议** | 尚未认定且未提存的争议金额 |

视图同时给出专户 `已划入/已付/提存/可用` 四个金额（全部由追加流水派生）与五个闸门的 `evidenced / facts_ready / closed` 三态。

## 清算顺序与闸门对应关系

```
公告 CLOSURE_ANNOUNCED
  → 主体识别 LEGAL_ENTITY_IDENTIFIED（固定钱、货、设备的归属与承担）
  → 顾客登记（重复通知合并）→ 顾客选择 TRANSFER / REFUND
      ├─ 转移：顾客确认 → 产能校验 → ORDER_TRANSFERRED                       ┐
      └─ 退款：REFUND_APPROVED → 第一顺位支付 → 退款到账后 CLAIM_CLOSED        ┤→ ORDERS 闸门
  → 中央工厂停料 CENTRAL_FACTORY_HALT_ACKNOWLEDGED                            │
  → 食品安全处置 INVENTORY_DISPOSED（捐赠/食用/销毁/退厂；禁抵债转卖）          ┤→ FOOD 闸门
  → 租赁设备约还 → 租赁公司签收 ASSET_RETURNED                               ─┘→ LEASED_ASSETS 闸门
  → 持续计提 ACCRUAL_RECORDED → 登记义务 → 第二顺位付清（工资）               → EMPLOYEE_PAY 闸门
  → 房租水电第三顺位 → 供应商第四顺位（争议按额提存，方案确认）               → SUPPLIER_DEBT 闸门
  → 五闸齐 + 未结清单清空 → CASE_CLOSED
```

## 代码结构

| 文件 | 职责 |
| --- | --- |
| `contracts/domain.schema.json` | 全部事件类型、聚合归属、payload 必填契约（JSON Schema） |
| `src/validator.js` | 信封、版本、时间、事件-聚合归属、payload 必填校验，返回中文错误 |
| `src/event-store.js` | 只追加日志：`event_id` 幂等、版本单调递增、外部通知去重 |
| `src/projection.js` | 案件折叠：主体、权益、批次、款项、争议、流水、未结清单、五闸门 |
| `src/platform.js` | 全部业务命令与规则：选择/确认/转移/退款/处置/归还/争议/提存/瀑布/关闸/关闭 |
| `src/demo.js` | 文三路店完整困局走查（70 条事件，五闸齐后关闭） |

| `tests/` | 契约测试 + 18 个场景规则测试（全部可复现的拒绝路径） |

## 为什么这样记事件

- **付款只追加流水**：`PAYMENT_SETTLED` / `PAYMENT_REVERSED` / `AMOUNT_ESCROWED` 都有全局递增的 `entry_seq`，余额是流水折叠的结果；任何"修改旧付款"的需求都通过新增红冲实现，审计轨迹完整。
- **拒绝也是事实**：违法处置食品、越权处置租赁资产、超范围冻结都发事件留痕（`DISPOSITION_RULE_VIOLATION_REJECTED`、`FREEZE_REQUEST_REJECTED`），而不是只报错——监管、商场、总部需要看到"被拦过"。
- **版本从 1 单调递增**：同一聚合内事件严格排序；外部系统重试沿用原 `event_id`，内容一致吸收、不一致拒绝。
